# Agnusmail protocol v1 — specification (DRAFT)

- **Status:** DRAFT 0.2 — **not externally reviewed yet**. An independent cryptographic
  review is welcome; until then, every part relies on the test vectors of §14 and on
  passing interoperability tests.
- **Principle:** this protocol **defines no new cryptographic primitives or formats**. It
  only fixes a profile of existing standards and the rules for using them:
  - OpenPGP — RFC 9580 (v6 keys, SEIPDv2/AEAD, Argon2 S2K);
  - OpenPGP PQC — RFC 9980 (ML-KEM-768+X25519, algorithm 35);
  - EIP-712 — attestations signed by the account's Ethereum wallet;
  - EIP-4361 (SIWE) — login.
- The key words **MUST**, **MUST NOT**, **SHOULD** and **MAY** are to be interpreted as
  described in RFC 2119 and RFC 8174.
- Items that need a reviewer's judgment are marked **[Q-nn]** and listed in §15.

## 1. Goals, non-goals and what the server sees

**Goals**
1. The server can never decrypt messages, attachments or backups.
2. The server cannot **replace** a device's key without the owner's wallet (EIP-712
   certificates, §4).
3. Messages between Agnusmail users are end-to-end encrypted, with post-quantum
   confidentiality (hybrid ML-KEM-768+X25519).
4. A new device can receive the message history without the server rewriting messages
   (§6.4).
5. Losing every device is recoverable with the recovery key; losing the wallet is
   recoverable with the recovery key and a 7-day waiting period (§8.5).

**Non-goals (accepted and documented risks)**
- The server **can omit** devices or keys from the directory, or show different views to
  different senders (there is no transparency log).
- Signatures are Ed25519 (not post-quantum) in v1. "Harvest now, decrypt later" affects
  encryption, which is hybrid.
- Routing metadata is visible to the server (list below).
- External messages received over SMTP are not end-to-end encrypted from their origin
  (§9).

**Metadata the server sees:** sender account and recipient accounts; fingerprints of the
recipient devices (they are in the PKESKs); time of sending; ciphertext size; delivery
and read state reported by the client. **It does not see:** subject, body, attachment
names and types, MIME headers, the Bcc list of other recipients.

## 2. Identities and identifiers

| Identifier | Definition |
|---|---|
| Account | Ethereum EOA address (20 bytes; lowercase in the API). EIP-1271 (contract wallets) is not supported yet. |
| E-mail address | `name@service-domain`, bound to one account. |
| `service` | Canonical identifier of the instance (e.g. `mail.example.com`), equal to the SIWE domain. It separates instances (the code is open source and may be forked). |
| Key fingerprint | OpenPGP v6 fingerprint (RFC 9580 §5.5.4): SHA-256, 32 bytes. |
| Device fingerprint | The v6 fingerprint of the **primary** key of the device certificate. |
| `message_id` | 128 random bits generated by the client, as lowercase hex (32 characters). |

`material_digest` is only a content digest of the stored blob; it is not a protocol
identifier.

## 3. Device certificate

Each device generates an OpenPGP v6 certificate locally. The private key never leaves the
device (except for the recovery key, §8).

### 3.1 Required structure

The profile follows the structure that OpenPGP libraries generate by default (Sequoia,
RFC 9580 profile), as checked by the tests.

| Component | Algorithm | Key flags (RFC 9580 §5.2.3.29) |
|---|---|---|
| v6 primary key | Ed25519 (27) | certify (0x01); sign (0x02) allowed (OpenPGP.js default) |
| v6 signing subkey | Ed25519 (27) | sign only (0x02), with a back-signature (required by RFC 9580) |
| v6 encryption subkey | ML-KEM-768+X25519 (35, RFC 9980) | encrypt communications (0x04) and storage (0x08) |

- v6 signatures (direct-key on the primary, subkey binding on the subkeys), with a hash of
  at least 256 bits (SHA-256/384/512, SHA3-256/512).
- **Expiration is required**, at most 2 years ahead.
- **No User ID** or User Attribute packets — the binding to the account is the EIP-712
  certificate (§4). [Q-01]
- No secret key packets. Preferences (AEAD, ciphers) **SHOULD** indicate AES-256 + OCB,
  but the server does not require them: protocol senders use fixed parameters (§6.2).
- Format label in the directory (`public_keys.format`): `openpgp-v6/agnusmail-device-1`
  (the only one accepted).
- There is no dedicated authentication subkey. Session authentication (§5) and the proof
  of possession (§3.3) use the signing subkey, with domain separation by the prefix
  `agnusmail/<use>/v1\n` in the signed text. Message signatures cover MIME literal data,
  which never starts with that prefix; a client **MUST NOT** sign, outside these flows,
  data that starts with `agnusmail/`.

### 3.2 Validation by the server

On publication, the server rejects the certificate if any item fails
(`src/agnusmail/infrastructure/openpgp.py`, on Sequoia/`pysequoia`):
1. format `openpgp-v6/agnusmail-device-1`; size ≤ `max_public_key_bytes` (8192);
2. a textual barrier against private key encodings; binary form (ASCII armor is refused);
3. packets: no secret key (tags 5/7); only a public key, subkeys and signatures; exactly
   one primary key;
4. Ed25519 v6 primary (32-byte fingerprint); exactly one Ed25519 subkey and one
   ML-KEM-768+X25519 subkey;
5. **every** self-signature of each v6 component uses a strong hash and exactly the flags
   of §3.1 (a certificate accumulates self-signatures; the library uses the newest valid
   one, so every one of them must be in the profile);
6. not revoked; expiration present, in the future and ≤ 2 years (checked explicitly: the
   library still encrypts to an expired certificate);
7. **functional validity of the bindings** (the library accepts corrupted signatures when
   parsing): encrypting an empty message to the certificate must work (binding of the
   encryption subkey) and the proof of possession of §3.3 must verify (binding and
   back-signature of the signing subkey). Nothing is decrypted.

### 3.3 Proof of possession

- Together with the certificate, the client sends a **detached** OpenPGP v6 signature,
  type 0x00 (binary), made by the **signing subkey**, over:
  `"agnusmail/key-registration/v1\n" || service || "\n" || account (lowercase) || "\n" || hex(primary fingerprint)`.
- The server requires it to verify, and the signing key to be the certificate's signing
  subkey. Since the text names the account and the service, the proof cannot be reused by
  another account or another instance.
- The primary fingerprint is fixed on the device and unique across all devices: the same
  certificate cannot represent two devices.
- Encryption subkey: OpenPGP has no proof of possession for an encryption-only key.
  Attaching someone else's encryption subkey only makes the attacker receive messages it
  cannot read. Accepted risk **[Q-03]**.

### 3.4 Rotation

- The encryption subkey **SHOULD** be rotated every 12 months: a new subkey and binding on
  the same primary, and the previous one becomes "superseded" in the directory. The device
  keeps the old secret key to read the history.
- Rotating the subkey does not need the wallet: the EIP-712 certificate binds the
  **primary** key.
- Every new version of a device **MUST** keep the same primary; the server refuses another
  one.
- Changing the primary key means a new device (a new EIP-712 certificate).

### 3.5 Local storage of the secret key (client requirement)

The server takes no part: nothing in this section reaches it, except the refusal in the
last rule.

- The transferable secret key (RFC 9580) is kept in the browser only **encrypted**, in an
  IndexedDB record:
  `{version: 1, fingerprint, mode: "prf" | "device", credentialId?, salt?, iv, ciphertext}`.
- Encryption: AES-256-GCM (WebCrypto), a random 12-byte `iv` per write, AAD =
  `"agnusmail/device-key/v1\n" || hex(primary fingerprint)`. The AAD binds the record to
  its device.
- `prf` mode (preferred when the browser and the authenticator support it):
  - a passkey of the account, with `userVerification: "required"`;
  - PRF input `eval.first` = `salt`, 32 random bytes per device, stored in the record
    (not secret);
  - key = HKDF-SHA-256(IKM = PRF output, empty salt,
    info = `"agnusmail/device-key-wrap/v1"`), imported as non-extractable, never stored;
  - unlocking can share the `navigator.credentials.get` call of the passkey login: the
    client adds `extensions.prf` to the server's options.
- `device` mode (no PRF): an AES-256-GCM key generated with `extractable: false` and
  stored as a `CryptoKey` in IndexedDB.
- When PRF becomes available (a passkey registered later), the client **SHOULD**
  re-encrypt in `prf` mode and delete the `device` mode key.
- The decrypted key stays in memory only and **MUST** be discarded on logout. The client
  **MUST** call `navigator.storage.persist()` and **MUST** delete the record when it learns
  that the device was revoked.
- The PRF output **NEVER** goes to the server: the client removes
  `clientExtensionResults.prf.results` before sending the credential. The server refuses
  with 422 any credential that carries it.

## 4. Wallet attestations — EIP-712

### 4.1 Domain

```
EIP712Domain(string name,string version,uint256 chainId)
name    = "Agnusmail"
version = "1"
chainId = the chain id configured for SIWE (default 1)
```

There is no `verifyingContract`: there is no contract. Instances are separated by the
`service` field of each message.

### 4.2 Types

```
DeviceCertificate(address account,bytes32 deviceFingerprint,string service,uint64 issuedAt,uint64 expiresAt)
DeviceRevocation(address account,bytes32 deviceFingerprint,string service,uint64 revokedAt)
RecoveryKeyCertificate(address account,bytes32 recoveryFingerprint,string service,uint64 issuedAt)
AccountMigrationAcceptance(address oldAccount,address newAccount,bytes32 recoveryFingerprint,string service,uint64 issuedAt)
PasskeyRegistration(address account,bytes32 credentialHash,string service,uint64 issuedAt)
```

`PasskeyRegistration` approves a login passkey; `credentialHash` = SHA-256 of the
WebAuthn credential id; `issuedAt` at most 10 minutes before the registration.

- Times in Unix seconds, UTC.
- `expiresAt - issuedAt` ≤ 400 days (the client renews before expiry).
- `deviceFingerprint` and `recoveryFingerprint` are the 32 bytes of the primary's v6
  fingerprint.
- The wallet signs with `eth_signTypedData_v4`.

### 4.3 Verification (by the server and by every sender)

1. 65-byte signature `r || s || v`, `v ∈ {27, 28}`, `s ≤ n/2` (EIP-2); otherwise reject.
2. Recover the address from the EIP-712 digest; it **MUST** equal `account`.
3. `service` and `chainId` **MUST** be the instance's; `deviceFingerprint` **MUST** be the
   one of the published OpenPGP certificate.
4. `issuedAt ≤ now + 5 min` and `now < expiresAt`.
5. A valid `DeviceRevocation` for the same fingerprint cancels the certificate.

### 4.4 Effect on the device lifecycle

- The device first publishes its OpenPGP certificate (§3), which fixes the fingerprint.
- `POST /v1/devices/{id}/authorize` receives `issued_at`, `expires_at` and the signature;
  the server fills in `account` (the session's account), `deviceFingerprint` (fixed on the
  device) and `service`/`chainId` (configuration), and verifies (§4.3). If valid, the
  device goes from `pending` to `active`.
- The same route renews the certificate of an active device; `issuedAt` must be newer
  than the current one (event `device.certificate_renewed`).
- Revocation optionally accepts a `DeviceRevocation` signed by the wallet.
- The directory (`GET /v1/keys/{address}`) returns `service`, `chain_id`, each key with
  its `device_certificate` (`issued_at`, `expires_at`, `signature`) and the signed
  `revocations`. A device key whose wallet certificate has expired is not published.
- The **sender** verifies all of this locally; it does not trust the server's `status`
  field to accept a key, only to exclude one.

## 5. Session bound to a device

1. After the SIWE login, the client asks for a challenge: `POST /v1/auth/device/challenge`
   with `{"device_id": ...}` of an **active** device of its own account. The server
   returns 32 random bytes (`challenge`, hex), bound to the session, single-use, valid for
   120 s, and the exact text to sign (`statement`).
2. The device makes a detached OpenPGP v6 signature, type 0x00 (binary), with the
   **signing subkey**, over the ASCII bytes:
   `"agnusmail/device-session/v1\n" || service || "\n" || hex(fingerprint) || "\n" || hex(challenge)`.
   The client checks that the received text has exactly this format before signing.
3. `POST /v1/auth/device/bind` with `{"device_id", "signature"}` (base64). The server
   consumes the challenge, verifies the signature with the device's active certificate
   (the signing key must be the signing subkey), stores `device_id` in the session and
   records `auth.session_bound` in the audit chain.
4. Revoking a device revokes the sessions bound to it (an index per device in Redis). If
   that revocation fails, the `DeviceSession` dependency checks in the database, on every
   request, that the device is still active; otherwise it ends the session.
5. Message, attachment and recovery routes **MUST** require a session bound to an active
   device (`DeviceSession`). An unbound session can only manage the account and its
   devices. `GET /v1/auth/device` shows the bound device.

This use of signatures is separated from message signatures by the domain prefix (§3.1),
not by a dedicated subkey.

## 6. Messages between users

### 6.1 Inner content (what the recipient decrypts)

- A complete RFC 5322/MIME message, with the **protected headers** inside it: `From`,
  `To`, `Cc`, `Date`, `Subject` and `Message-ID: <{message_id}@{service}>`.
- Each Bcc recipient gets a separate message, with its own `message_id`.
- Signed by the sending device with the **signing subkey**: a signed OpenPGP message
  (one-pass signature + literal data + signature, v6, SHA-512), then encrypted.
- **No compression:** the compressed data packet (tag 8) **MUST NOT** be used; the
  receiver rejects it. Reasons: compression side channels and decompression bombs.

### 6.2 Encryption

- SEIPD **v2** (tag 18), AES-256 (9), OCB (2). Chunk size: any value allowed by RFC 9580
  (octet 0–16); Sequoia uses 6 (4 KiB). The server refuses another AEAD, another cipher
  and a chunk size above 16.
- One **v6** PKESK per active encryption subkey of:
  1. each active device of each recipient;
  2. each active device of the sender (Sent folder);
  3. the recovery key of each account involved (§8).
- The PKESK **MUST NOT** be anonymous (wildcard): the server must route it.
- No custom AAD: SEIPDv2 already authenticates its own parameters. The binding to the
  metadata comes from the protected, signed headers (§6.6), not from a new construction.

### 6.3 Storage

- The body (the SEIPDv2 packet) is stored once.
- Each PKESK becomes one row, per (message, device key).
- A device's OpenPGP message is `PKESK(device) || SEIPDv2`, which is already a valid
  OpenPGP message. The server only concatenates; it never opens anything.

### 6.4 History for a new device

An already active device (or the recovery key, §8):
1. decrypts its own PKESK;
2. obtains the session key;
3. creates a v6 PKESK for the new device;
4. sends only the new PKESK.

The server checks the structure and that the fingerprint belongs to an active device of
the same account. No message is rewritten.

### 6.5 Sending and validation by the server

Routes (all require a session bound to a device, §5): `POST /v1/messages`,
`GET /v1/messages?folder=inbox|sent|trash`, `GET /v1/messages/{id}` (body + the PKESKs of
the session's device), `POST /v1/messages/{id}/move`, `/read` and `/keys` (§6.4). The
server reads only the fingerprint in the v6 PKESK header and the parameters of the
SEIPDv2 header, on packets split by the library. "Published keys" follow the directory
rules (active, unexpired key of an active device with a valid wallet certificate). The
body is limited to `max_message_bytes` (512 KiB; larger content goes in attachments, §7).

`POST /v1/messages`:

```
{ "version": 1, "message_id": "<32 hex>",
  "recipients": [ { "account": "0x…", "pkesks": ["<base64>", …] } ],
  "self_pkesks": ["<base64>", …], "body": "<base64 SEIPDv2>" }
```

The server **MUST**:
1. accept `version` = 1 and no other value;
2. refuse a `message_id` repeated by the same sender (idempotency and anti-replay);
3. parse each PKESK: v6, algorithm 35, fingerprint of an active encryption subkey of an
   active device of the given account (or of its recovery key);
4. require **completeness**: every active device and the recovery key of each account
   with its PKESK; otherwise answer 409 with the current directory version (the client
   fetches again and encrypts again);
5. parse the body: exactly one tag 18 v2 packet, AES-256, OCB, chunk size within the
   limit, size ≤ limit; nothing after it;
6. never try to decrypt, and store nothing beyond what was received.

### 6.6 Verification by the recipient (anti-replay and anti-substitution)

The decrypting client **MUST** verify:
1. a valid signature by the primary key of one of the sender's devices, and that device
   having a valid `DeviceCertificate` for the sending account;
2. the inner `Message-ID` equals `<{message_id}@{service}>` of the envelope;
3. its own address in `To`/`Cc` (or a Bcc message addressed to it);
4. the inner `From` equals an address of the sending account.

This way the server cannot reuse the body of one message in another, nor change the
sender or recipient, without the client noticing. It can still deliver the same message
to the same recipient again; the client discards a repeated `message_id`.

## 7. Attachments

- Small attachment (≤ the body limit): a normal MIME part inside the message.
- Large attachment: a separate object, SEIPDv2 (AES-256/OCB) with **its own random
  session key**. Inside the encrypted message goes an
  `application/vnd.agnusmail.attachment+json` part with:
  - `object_id`;
  - file name and MIME type;
  - algorithm and session key (base64);
  - `sha256` of the ciphertext.
- The receiver downloads the object, checks the SHA-256 and decrypts with the session key.
  OpenPGP libraries already support decrypting with a known session key.
- The file name and type never appear outside the ciphertext.
- API: `POST /v1/attachments` {`size`, `sha256`} returns a presigned PUT URL (the size is
  bound to the signature, 15 min); the client uploads the SEIPDv2 directly to the storage;
  `POST /v1/attachments/{id}/complete` checks the size; `POST /v1/messages` takes
  `attachments: [id]` (only ids are visible to the server), which allows the participants
  to download it; `GET /v1/attachments/{id}` returns a presigned GET URL (60 s). The
  worker deletes orphans. The server does not read the content.
- **[Q-04]** review this use of a session key carried inside the message (alternative:
  one PKESK per device for each attachment as well).

## 8. Recovery key and backup

### 8.1 Recovery secret

256 random bits generated on the client, shown as 24 BIP-39 words (English list, with
checksum). BIP-39 is only an **encoding** of the entropy; the BIP-39 PBKDF2 seed
derivation is not used. The server never receives the words.

### 8.2 Recovery certificate

- The client generates, **with fresh randomness** (not derived from the phrase), a v6
  certificate with the same structure as §3.1. It is a "virtual device" that never comes
  online.
- Directory label: `openpgp-v6/agnusmail-recovery-1`.
- The wallet attests it with `RecoveryKeyCertificate`.
- Its encryption subkey receives a PKESK in every message of the account (§6.2).

### 8.3 Backup

- Content: the transferable secret key of the recovery certificate (RFC 9580), inside a
  symmetric OpenPGP message:
  - v6 SKESK with Argon2 S2K (RFC 9580 §3.7.1.4): t = 1, p = 4, m = 2^16 KiB — the input
    already has 256 bits of entropy, so the parameters only need to be decent;
  - SEIPDv2 with AES-256/OCB.
- The S2K passphrase is the 24 words, normalized: NFKD, lowercase, separated by a single
  space.
- Only the encrypted backup goes to the server (`recovery_backups`, versioned,
  ≤ 64 KiB). The server never receives the phrase or the passphrase.
- The server checks only the structure (without decrypting): exactly one v6 SKESK
  followed by one SEIPDv2; Argon2 S2K with t ≥ 1, p ≥ 4, m ≥ 2^16 KiB; AES-256/OCB.
  Otherwise: 422.
- A backup can only be stored after a recovery key is registered (409 without one).

### 8.4 Restore

The new device:
1. downloads the backup: with a session, `GET /v1/recovery/backup`; **without a session**
   (the wallet is lost and there is no passkey or logged-in browser),
   `POST /v1/recovery/backup/fetch` `{account}` with the old wallet address or the
   account's e-mail address. Only the blob comes back. An unknown account, or one without
   a backup, gets a decoy backup with the same structure as a real one (framing,
   algorithms and Argon2 parameters of the oldest stored backup), stable for the same
   query (HMAC-SHA-256 with `recovery_decoy_secret`): the route does not reveal which
   accounts exist. Rate-limited per IP. With the wrong words, the real and the decoy
   backup fail the same way;
2. decrypts it locally with the 24 words;
3. with the recovery key, creates PKESKs for itself across the history (§6.4);
4. asks the wallet for a `DeviceCertificate` for itself.

### 8.5 Lost wallet — account migration

1. With the recovery key restored, the client builds the migration request:
   - a detached OpenPGP v6 signature (type 0x00) by the **signing subkey of the recovery
     certificate** (like the proofs of §4) over
     `"agnusmail/account-migration/v1\n" || service || "\n" || oldAccount || "\n" || newAccount || "\n" || issuedAt`;
   - an `AccountMigrationAcceptance` signed by the **new wallet** (it proves control of
     it);
   - `issuedAt` is valid for 10 minutes (with 5 minutes of clock tolerance); the request
     is made without a session, and every rejected proof gets the same answer
     (422 `MIGRATION_REJECTED`);
   - refused with 409 if the new wallet already has an account or a migration is already
     pending.
2. The server verifies both signatures and that the recovery certificate was attested by
   the old wallet. Then it:
   - opens a **7-day** waiting period;
   - warns every device: the event `recovery.migration_requested` goes into the account's
     audit chain, and every client checks `GET /v1/recovery/migrations` when it opens and
     periodically, showing a warning that cannot be dismissed while a migration is
     `pending` (there is no push or e-mail notice in this version);
   - accepts cancellation from **any authenticated session of the account** — SIWE login
     with the old wallet, or a passkey approved by it, bound to a device or not
     (`POST /v1/recovery/migrations/{id}/cancel`). Cancelling only protects the owner;
     requiring a device binding would delay an owner who lost the devices but still has
     the wallet.
3. When the period ends, a worker job (hourly) moves the account to the new wallet and
   ends all its sessions. If the new wallet opened an account in the meantime, the
   migration is cancelled (accounts are never merged). The chain becomes a public proof,
   published in the directory (`migrations`):
   `old wallet → RecoveryKeyCertificate → migration → new wallet`.
4. Senders verify the chain. A `DeviceCertificate` from the old wallet issued **after** the
   migration took effect **MUST NOT** be accepted. [Q-10]

The recovery key is **generated randomly and protected** by the recovery secret; it is
never derived from the phrase, so that no Ed25519/ML-KEM key derivation from a phrase has
to be invented.

## 9. Inbound SMTP gateway

- The gateway receives the external MIME message in clear (over TLS) and does not store
  it: it answers 250 only after encrypting and storing the ciphertext.
- It builds the same structure as §6: PKESKs for the recipient's active devices and
  recovery key, and a SEIPDv2. It verifies each `DeviceCertificate` like any sender.
- Before encrypting, it adds `Authentication-Results` (RFC 8601) with SPF/DKIM/DMARC
  (computed by Rspamd, §9.2) and signs the message with the **gateway key**. This attests
  "received by this gateway"; it does not authenticate the external sender.
- **Gateway key:** a v6 certificate with an Ed25519 primary and an Ed25519 signing
  subkey, valid for 2 years and **without an encryption subkey** — the gateway has no
  decryption key at all (the library generates one, which is removed before writing; every
  load proves that encrypting to the certificate fails). The signature is the one of §6.1:
  a signed message (one-pass + literal + v6 signature, SHA-512), then encrypted. The secret
  key comes from a file (`AGNUSMAIL_INBOUND_SIGNING_KEY_FILE`, created by
  `python -m agnusmail.apps.smtp_inbound generate-key`, mode 0600, never overwritten).
- **Publication:** `GET /v1/gateway/keys` (public, no session) lists every certificate
  ever used, oldest first, and never deletes one: old messages stay verifiable after a key
  change. The gateway publishes its own certificate before accepting connections.
- **Verification by the client (message with `origin = external`):** exactly one valid
  signature by a certificate from `GET /v1/gateway/keys`. Without it, the client **MUST**
  treat the message as untrusted. The guarantee is limited: the server publishes the list,
  so it only attests "came through this service's gateway".
- The client **MUST** show "external message, encrypted on arrival (not end-to-end
  encrypted from its origin)".
- The gateway has no user decryption key. **[Q-06]** what to do with an external message
  that already arrives OpenPGP-encrypted to the user (e.g. keep the received PGP/MIME as
  the body, encrypted again).

### 9.1 Receiving

- A separate process (`python -m agnusmail.apps.smtp_inbound`, aiosmtpd), everything in memory; core
  dumps are disabled at startup; aiosmtpd's `mail.log` logger stays at WARNING (at INFO it
  logs IPs and addresses; at DEBUG, every DATA line).
- `RCPT`: only active addresses of the service. Unknown → `550 5.1.1`; after
  `inbound_max_unknown_recipients` (5) unknown recipients on the same connection → `421`
  and the connection closes. Account without a device key → `450 4.2.1`. Account
  suspended or storage full → `452 4.2.2`. Above `max_message_recipients` → `452 4.5.3`.
- `DATA`: maximum size = `max_message_bytes` − 32 KiB (`552` above that). One message per
  recipient account, each with `Return-Path` and `Received` (RFC 5321 §4.4) **inside** the
  encrypted content — the client IP and the envelope do not stay outside the ciphertext.
  Values coming from the SMTP client are reduced to printable ASCII (no header
  injection).
- Encryption: a v6 PKESK for each published key of the recipient (active devices and
  recovery key) and a SEIPDv2 checked by the same rules as §6.5. Before using a key, the
  gateway checks the wallet attestation again (`DeviceCertificate` or
  `RecoveryKeyCertificate`), accepting the current wallet or a previous one for
  attestations issued before a migration (§8.5). A key without a valid attestation is
  skipped.
- Everything in one transaction; `250` only after the commit. Any failure →
  `451 4.3.0` and nothing stored. Exception texts never go to the log.
- Stored with `origin = external` and no sender; the API returns `"origin": "external"`
  and `"sender": null`.
- **Limitation:** messages larger than the limit (large external attachments) are refused
  with `552`.

### 9.2 Antispam before encryption

- The gateway sends the in-memory message to Rspamd (`POST /checkv2`, internal network)
  with the envelope in headers (`IP`, `Helo`, `From`, one `Rcpt` per recipient) and its
  own name in `MTA-Name` (authserv-id). Once per transaction, before encrypting.
- Action `reject` → `550 5.7.1`; `soft reject` and `greylist` → `451 4.7.1`; Rspamd down
  or an unexpected answer → `451 4.3.0` (fail closed: the sender retries). Nothing is
  stored.
- Accepted: inside the encrypted content, right after `Return-Path`, go
  `Authentication-Results` (Rspamd's; `<host>; none` when it ran no checks), `X-Spam:
  Yes|No` and `X-Spam-Score`. Copies of these three fields coming from outside are always
  removed (RFC 8601 §5), as are those Rspamd asks to remove. Values that are not
  printable ASCII with valid folding are dropped (no header injection).
- Accepted spam (`add header`) goes to the inbox marked `X-Spam: Yes` inside the
  ciphertext; the server does not store the verdict.
- Rspamd neither keeps nor sends to third parties anything derived from the content (see
  `docker/rspamd/README.md`).
- Outside the local environment, the gateway does not start without
  `AGNUSMAIL_INBOUND_RSPAMD_URL`.
- **Operational note:** Rspamd skips SPF/DKIM/DMARC for IPs of its own local networks
  (127/8, 10/8, 172.16/12, 192.168/16). The gateway must see the sender's real IP: no
  `docker-proxy` or load balancer that rewrites the source IP (see §9.3).

### 9.3 Connections and operation

- **TLS:** STARTTLS offered with TLS 1.2+ and the library's secure defaults; never
  required (RFC 3207 §4, public MX). `Received` records `ESMTPS`. Outside the local
  environment the gateway does not start without a certificate and key
  (`AGNUSMAIL_INBOUND_TLS_CERT_FILE`/`_KEY_FILE`; the key file has the same permission
  check as the signing key).
- **Per connection:** idle timeout (120 s), maximum duration (600 s — a client that sends
  DATA slowly renews the idle timeout on every line), 100 calls per command, at most 200
  simultaneous connections and 10 per IP (above that, `421` instead of the greeting).
- **Per IP and hour (Redis, across connections and processes):** 30 unknown recipients
  (→ `421` and close) and 300 messages (→ `451`). With Redis down, these two limits let
  traffic through and the error is logged, like the API's limits.
- **Its own database role** (`GATEWAY_TABLE_PRIVILEGES`): SELECT on `users`,
  `mail_addresses`, `mail_domains`, `devices`, `public_keys`, `recovery_keys`,
  `account_migrations`; INSERT on `messages`, `message_keys`, `mailbox_entries`; SELECT,
  INSERT and UPDATE on `account_usage`; SELECT and INSERT on `gateway_keys`; nothing else.
  It reads no message back, no audit, mailbox, session or job data. Outside the local
  environment the gateway does not start with any privilege beyond that map. Provisioned
  by `python -m agnusmail.infrastructure.database.roles` when
  `AGNUSMAIL_DB_GATEWAY_PASSWORD` is set.
- **Sender's real IP:** behind a TCP load balancer, PROXY protocol v1/v2 is accepted only
  from `AGNUSMAIL_INBOUND_TRUSTED_PROXIES` (any other peer is closed before the greeting).
  The real IP goes to `Received`, Rspamd and the hourly limits; the per-IP connection
  limit counts the load balancer. Without a load balancer, publish the port preserving the
  source IP. Outside the local environment, a non-public client IP is logged once (a sign
  of misconfiguration: Rspamd would skip SPF/DKIM/DMARC).

### 9.4 No plaintext persists

- **Process:** `RLIMIT_CORE = 0` and `prctl(PR_SET_DUMPABLE, 0)`. The latter is what
  matters when the kernel's `core_pattern` pipes the dump to a program (systemd-coredump,
  WSL): in that case the kernel ignores `RLIMIT_CORE`. Outside the local environment the
  gateway does not start without both.
- **Container:** read-only root without tmpfs, no swap (`memswap_limit = mem_limit`), no
  capabilities, `init` as PID 1 (PID 1 ignores signals without a handler, and the init
  process does not forward synchronous signals such as SIGSEGV).
- **Automated proof** (`tests/integration/test_inbound_no_plaintext.py`): a random marker
  in the envelope, `Subject` and body of delivered, failed and refused messages is
  searched in every column of every table (text and hex of bytea) and in every Redis key
  and value, with positive controls that prove the search finds it.
- **Proof on the real containers** (`scripts/inbound-no-persistence.sh`, a release check):
  an accepted message, one refused by Rspamd (GTUBE) and one too large; the gateway is
  killed with SIGSEGV; the marker is searched in the gateway's filesystem (no change at
  all) and key volume, Rspamd's filesystem, the logs of the gateway, Rspamd and API, the
  database and Redis; it checks the read-only root, the absence of swap and that the
  process is not dumpable.
- **Fuzzing** (Hypothesis, `tests/unit/test_inbound_fuzz.py`; `HYPOTHESIS_PROFILE=deep`):
  packet splitting and envelope checks, header removal, Rspamd answers, trace headers and
  the SMTP server with arbitrary lines. The header block ends only at the first empty
  line, names with a space before the `:` (obsolete syntax) are recognized and a lone `CR`
  does not break a line. The client **MUST** use the first occurrence of these fields (the
  gateway's, always at the top).
- **Load** (`tests/integration/test_inbound_load.py`): 20 KiB messages on 12 simultaneous
  connections, none lost or duplicated (`AGNUSMAIL_LOAD_MESSAGES` for larger runs).

## 10. Conventional outbound SMTP — not end-to-end encrypted

- The client decrypts locally and sends the ready content to the outbound service, over
  TLS. The channel is labeled **not end-to-end encrypted**.
- The 72-hour encrypted queue is encryption **at rest** of content that the user handed
  over in clear for external delivery. The key exists only in the outbound service and
  never applies to end-to-end encrypted messages.
- The outbound service decrypts its own queue. This is the **single, narrow exception** to
  "the backend cannot decrypt": the key exists only in that service and never applies to
  E2EE messages, attachments, backups or user keys. A test guards that no other module
  decrypts (`tests/unit/test_outbound_service.py`).

### 10.1 Submission to the queue

1. The client fetches `GET /v1/outbound/keys` (public; newest first) and encrypts the
   ready MIME message **only** to that key: exactly one v6 PKESK (algorithm 35) +
   SEIPDv2 AES-256/OCB — the same profile as §6.2. The queue key follows the device
   profile (§3.1).
2. The MIME message **MUST** be 7-bit (bodies in quoted-printable or base64), with lines
   of at most 998 octets and exactly one `From:` equal to the user's address.
3. `POST /v1/outbound/messages` (session bound to a device):
   `{version: 1, message_id, recipients: [...], payload, sent_copy?}`. `recipients` are
   the envelope recipients (Bcc included), as dot-atom with a DNS domain; addresses on the
   service's own domain (and subdomains) are refused — `RECIPIENT_INTERNAL`: they go
   through the E2EE channel. `sent_copy` (`{pkesks, body}`) is the sender's E2EE copy for
   the Sent folder, with the same completeness rule as §6.5 (`origin = outbound`).
4. Answers: `202` with the state; `409 SENDER_ADDRESS_REQUIRED` (no address),
   `409 OUTBOUND_KEY_CHANGED` (encrypted to another key), `503 OUTBOUND_UNAVAILABLE` (no
   key published), `422 ENVELOPE_INVALID`, `429` (limits: messages per hour, recipients
   per day; without Redis, 503). Every answer carries `protection = "not-e2ee"`.
5. State: `GET /v1/outbound/messages[/{id}]` — per recipient, `pending`, `delivered` or
   `failed`, with the SMTP code and the enhanced status code (never the server's text).

### 10.2 Delivery

- Service `agnusmail.apps.smtp_outbound`, with its own process and database role
  (`OUTBOUND_TABLE_PRIVILEGES`: only the queue tables), non-dumpable, read-only container
  and no swap.
- Claims with `FOR UPDATE SKIP LOCKED` and a lease; decrypts in memory; applies the policy
  (`From` = sender, `Sender` likewise, single-occurrence fields, 7-bit, lines ≤ 998,
  removes `Bcc` and server fields such as `Received`, `DKIM-Signature`, `ARC-*`,
  `Authentication-Results`; adds `Date` and `Message-ID` if missing); signs with DKIM
  (RSA-2048/SHA-256, relaxed/relaxed, `From` oversigned; `d =` the service's domain).
- Delivery per domain: MX hosts in preference order (without MX, the A/AAAA; the RFC 7505
  null MX = permanent failure). **Only public addresses** are contacted (an MX pointing at
  an internal network is refused). STARTTLS whenever offered (TLS ≥ 1.2, opportunistic);
  `AGNUSMAIL_OUTBOUND_REQUIRE_TLS` requires it. `MAIL FROM` = the user's address.
- 2xx delivered; 5xx permanent failure; 4xx, network or DNS error: retry in 5 min,
  doubling up to 3 h. When a message is done, its ciphertext is deleted in the same
  transaction that records the result.
- Expiry: `expires_at` = submission + 71 h 50 min; the database refuses more than 72 h
  (CHECK). The service itself expires messages on every round and the worker
  (`outbound.purge`, every 10 min) does the same while the service is stopped. Delivery
  records (addresses and codes) are deleted 30 days after they finish.
- DNS records: `python -m agnusmail.apps.smtp_outbound dns-records` prints SPF, DKIM and DMARC
  (`p=reject`, strict alignment); the PTR of the outbound IP must point to
  `AGNUSMAIL_OUTBOUND_HOSTNAME`.

## 11. Secure portal

- The sender builds an OpenPGP message with:
  - a v6 SKESK, Argon2 S2K with t = 3, p = 4, m = 2^16 KiB (the second recommendation of
    RFC 9106, feasible in a browser);
  - SEIPDv2 AES-256/OCB;
  - PKESKs for its own devices.
- The password **MUST** be generated by the client with ≥ 80 bits of entropy (e.g. 7 words
  from the EFF list). The user passes it to the recipient through another channel. A
  password chosen by the user **MUST NOT** be accepted: the server stores the ciphertext
  and could test weak passwords offline.
- Expiry ≤ 30 days; after that the server deletes the ciphertext.
- Classification: **end-to-end encrypted with a shared secret**. Known limitation: the
  server delivers the portal code to the browser and could deliver malicious code
  (mitigation: reproducible builds and Subresource Integrity on the client side).
- Replies are supported: the recipient's browser encrypts to the sender's devices and
  recovery key (directory and EIP-712 attestations delivered by the portal).

### 11.1 API

- `POST /v1/portal/messages` (session bound to a device):
  `{version: 1, message_id, recipients, expires_in_days (1–30), envelope, notify}`. The
  envelope has PKESKs for **exactly** the sender's published keys (§6.5; that is how the
  sender keeps its own copy), exactly one v6 SKESK (AES-256/OCB, Argon2 with t ≥ 3,
  p ≥ 4, m ≥ 2^16 KiB) and one SEIPDv2 AES-256/OCB, in this structure (PKESKs and SKESK in
  any order, SEIPD last). External recipients only (the service's own domain is
  refused). Answer `201` with `links` (`{recipient, url}`, `url` =
  `AGNUSMAIL_PORTAL_BASE_URL#token`) — **only at that moment**: the database keeps the
  SHA-256 of the token (256 random bits). `protection = "e2ee-shared-secret"`.
- `notify = true` (default): one notice per recipient, a fixed text built by the server
  (sender's address, link, expiry; never the content or the password), encrypted by the
  API to the outbound queue key and delivered by conventional outbound SMTP (it counts
  toward its limits; without an outbound service, `503 OUTBOUND_UNAVAILABLE`).
- Sender: `GET /v1/portal/messages[/{id}]` (state per recipient: replies and last access;
  the envelope in the detail) and `DELETE /v1/portal/messages/{id}`.
- Recipient (no session; the token goes in the JSON body of a `POST`, never in the URL; an
  unknown or expired token = 404; rate-limited per IP): `POST /v1/portal/access`
  (envelope, sender's address, expiry, remaining replies), `POST /v1/portal/keys` (the
  sender's directory, with the EIP-712 attestations for the browser to verify) and
  `POST /v1/portal/replies` (`{token, version, pkesks, body}`, same completeness rule as
  §6.5; goes to the sender's inbox with `origin = portal`; up to 5 replies per link). The
  server does not attest who replied.
- Expiry: the database refuses more than 30 days (CHECK); `portal.purge` (worker, every
  10 min) deletes envelope, links and tokens; reads after expiry already answer 404.
- A client requirement the server cannot verify: a password generated with ≥ 80 bits of
  entropy.

## 12. Versioning and evolution

- `version` = 1 in every message, backup and migration API. An unknown version is
  rejected, not interpreted.
- Algorithms outside this profile are rejected in v1 (agility only through a new
  version).
- Replacing Ed25519 with ML-DSA-65+Ed25519 (algorithm 30, RFC 9980) is planned for v2.

## 13. Libraries and interoperability

- **RFC 9980 was published in June 2026** (Standards Track). ML-KEM-768+X25519
  (algorithm 35) and ML-DSA-65+Ed25519 (30) are mandatory to implement.
- Public sources indicate support in OpenPGP.js, GopenPGP, Sequoia and rPGP.
  Interoperability **MUST** be proven by test vectors (§14), never assumed.
- Server side (validation, signature verification and encryption in the inbound
  gateway): `pysequoia` (Apache-2.0). For EIP-712: `eth-account`.

## 14. Test vectors

- **OpenPGP.js ↔ server + Sequoia interoperability:** `scripts/interop-openpgpjs.sh`, also
  in CI (job `interop`). The published OpenPGP.js (6.x) has no PQC; the test uses `main`
  (v7, not yet released) pinned to a reviewed commit, built in a throwaway container. The
  server accepts the certificate, the proof of possession, the session proof and the
  envelope generated by OpenPGP.js; Sequoia decrypts and validates the signature;
  OpenPGP.js decrypts and validates Sequoia's reply.
- **Requirements for OpenPGP.js clients** (found by the test):
  1. generate the key with `config: { v6Keys: true, aeadProtect: true,
     preferredAEADAlgorithm: ocb, preferredSymmetricAlgorithm: aes256 }` and
     `subkeys: [{ sign: true }, { type: 'pqc' }]`, without a User ID — otherwise the key
     does not announce SEIPDv2 and OpenPGP.js senders fall back to SEIPDv1;
  2. when encrypting, pass `sessionKey: { data: 32 random bytes, algorithm: 'aes256',
     aeadAlgorithm: 'ocb' }`: OpenPGP.js does not apply the implicit AES-256+OCB of
     RFC 9980 §7.1 and would fall back to AES-128 with Sequoia-generated recipients
     (which the server refuses);
  3. the OpenPGP.js primary has the certify + sign flags: accepted by the server (§3.1);
     the proofs still require the signing subkey.

Published EIP-712 vector (`tests/unit/test_attestation.py`; the digest is also computed by
hand in the test, independently of the library's encoder):

  example, no funds) → account `0x2c7536E3605D9C16a7a3D7b1898e529396a65c23`;
- `DeviceCertificate`: `deviceFingerprint` = `0x` + `ab`×32, `service` =
  `mail.example.com`, `issuedAt` = 1794484800, `expiresAt` = 1826020800, `chainId` = 1;
- EIP-712 digest = `680b5a9f31b67dd6648434cd9199d8eb40c0d91aff76c505480f2cb40b95e4e5`;
- signature (RFC 6979) =

Coverage of the groups below: 2, 3 and 5 by automated tests; 4 by the OpenPGP.js ↔
Sequoia interoperability test (without the extra PKESK case); 1 and 6 are still open.

1. Those of RFC 9980, Appendix A (v6 Ed25519 + ML-KEM-768+X25519).
2. Device certificates: valid; without a signing subkey or without PQC; with a v4
   encryption subkey; with a secret packet; expired; with wrong preferences.
